**[SUM]:** Confirms. [SUM]'s Phase 1 exit criterion, "a real customer completes buy → pay → provision → 'it works' unattended", requires Order & Provisioning in the MVP.

### C3
**Decision:** The [PO] sprint order is **authoritative** and is not re-sequenced. Phases define only what is in the MVP (C2). The MVP is complete at the end of sprint **2027.1.3**.
**Reason:** [PO] is the only dated plan. Every MVP application is scheduled by 2027.1.3, so the order no longer changes the MVP content. Dependency-ordering risks are handled inside each sprint's planning.

### C47
**Decision:** REQ-BIL-001 is built per C46, with the following pragmatic engineering assumptions where the FRD's own open questions are still unanswered by the product owner. ### C96
**Decision (product owner, 2026-10-13) — Tax calculation in two modes, chosen by a switch in Platform Admin → Billing → Tax Configuration ([REQ-BIL-002](../../02-requirements/FRD/tax-rules/requirement.md), replaces the admin-rate and fall-back design of [C51](#c51)):**
- **Switch External Tax Engine:** **Off** (default) = the EIS **internal** engine with region-based rules the platform administrator configures; **On** = the **external** tax provider. The choice is stored in the database (`tax_settings`), so it survives sign-out, restart and deployment. The screen shows the active mode and its status.
- **Internal engine:** rules by country, state or province, jurisdiction, tax type (GST, VAT, Sales tax, Other), several components per rule (CGST + SGST, IGST, state + county …), tax class, customer type, supply type (within state, between states, cross-border), customer tax ID condition, treatment (taxable, exempt, zero-rated, nil-rated, reverse charge, out of scope), effective-from and effective-to, **versions**, **approval** (draft → pending → approved, a second administrator approves) and **activation**. India: CGST + SGST within the seller's state and IGST between states, decided from the seller's state and the place of supply (the GSTIN state when valid, else the billing state). **No rate is written in code, the frontend or a migration.** Only approved, active, in-force and matching rules are used; no match means **blocked**, never a default rate or a silent zero.
- **External engine:** a provider **adapter interface** (nothing in billing depends on a vendor). The first adapter is a generic REST adapter with a documented contract. The flow is: supplier legal entity and registrations, customer billing details and tax IDs, product tax class, amount and currency → provider → response **validated** (status, reference, currency, amounts, arithmetic) → stored with the provider reference → invoice. Credentials stay in the **backend environment** ([BR-SEC-001](../../03-business-rules/BR-SEC-001-central-secrets-file.md)), never in the database or in a response. **Test connection** and **Validate capabilities** exist; External **cannot be switched on** until the provider is configured and passes the checks. Transient failures are retried (default 3 attempts, same idempotency key); a failure or invalid response **blocks the invoice**; there is **no silent fall-back** to the internal engine.
- **Switching:** only new calculations are affected. A calculation **pins** the mode at its start. An issued invoice never changes. A blocked invoice is a **Draft** (no number, not payable, hidden from the customer); **Retry tax** restarts it with the mode in force at that moment.
- **Defaults applied (not asked):**
  - **Maker and checker:** the administrator who last edited a rule cannot approve it. A platform setting "Allow the same administrator to approve" (off by default) lets a one-administrator installation work.
  - **Invoice date for rule dates:** the calculation date in UTC. **Rounding:** half up, per line and per component. **Compound components:** supported with a flag.
  - **Customer type:** Business when the invoice owner is an organization, otherwise Individual. **Tax ID condition:** Provided when billing details have a tax ID.
  - **Tax classes** (for example a SAC code) are a small admin list; each product has one optional class. A product without a class matches only rules whose class is Any; the external engine blocks it (the provider needs a class).
  - **Provider base URL, API key and secret come from environment variables** `TAX_PROVIDER_BASE_URL`, `TAX_PROVIDER_API_KEY`, `TAX_PROVIDER_API_SECRET` (the base URL is not editable on screen, so an administrator cannot point the backend at an arbitrary address). Provider code, company code, environment, timeout and attempts are editable.
  - **Credit notes** reverse the original invoice's tax lines in proportion; the provider is not told about credit notes (Not specified).
  - **No tax rates are seeded.** Until an administrator approves rules (or switches to a provider), paid invoices stay **Draft** and the screen says so. The accountant supplies the rules (India GST, other countries).
- **Behaviour change:** invoices were always issued with tax 0 (C47). They are now issued with the calculated tax, or held as Draft. Migration V036.
**Still Not specified:** which provider is contracted (vendor adapters follow); reporting credit notes and voids to the provider; amount thresholds on rules; withholding tax; e-invoicing (IRN, QR); tax-inclusive pricing; tax returns and filing.

**Decision (product owner, 2026-10-14) — the Payment Gateway page becomes provider-independent ([REQ-BIL-003](../../02-requirements/FRD/payment-gateways/requirement.md), extends [C97](#c97) BI-8):**
- **Provider registry.** Every payment provider is a backend adapter behind one interface plus a descriptor (name, countries, currencies, methods, transaction types, test and live support, webhook, refund and recurring support, configuration fields, setup steps, implementation status). The page lists what the registry says; adding a provider adds no UI code.

Stripe, PayPal, PayU and Cashfree are listed as **planned** (description and the fields they will need, no Configure, Test or Activate); nothing is simulated. **Amended by [C99](#c99):** the planned list is removed; an administrator can add any gateway, which stays configuration only (no integration) until a developer writes an adapter.
- **Independent gateways.** Each gateway has its own credentials, environment (Test or Live), enabled payment methods, webhook status and validation result. **Configured, Connected (last test), Active and Default are four separate statuses.** Several gateways can be active at once; one can be the **default**. Activating needs complete configuration and a passing live connection test for the current configuration version; changing the credentials of an active gateway re-tests it in the same request and **keeps the old credentials if the test fails**.
- **Credentials (changes BR-SEC-001 for this feature).** An administrator can now enter, replace and rotate credentials on the screen. They are **encrypted at rest (AES-256-GCM) with a master key from the environment variable `PAYMENT_GATEWAY_ENCRYPTION_KEY`** and are **write-only**: the API never returns a secret, only whether each field is set, where it comes from (stored or environment) and a masked public identifier. **Without the master key, saving credentials is refused.** Razorpay credentials already in the secrets file keep working; a stored value overrides the file. No credential is in source control.
- **Routing.** The backend picks the gateway for each new payment: active, configured, supports the invoice currency and the chosen payment method, default first. No eligible gateway means the payment cannot start and the customer sees a clear error. The browser never chooses a gateway. A payment keeps the provider that created it; changing the default or deactivating a gateway never changes completed payments, refunds or subscriptions (a refund or reconcile goes to the payment's own provider).
- **Webhooks.** One endpoint per provider, `POST /webhooks/{provider}`, signature-verified by that provider's adapter, idempotent per provider and event id (migration V038 makes the event id unique per provider). The screen shows the endpoint (built from `app.backend-url`), the provider's setup steps, the last event received and the recent failures. Webhooks are accepted for any configured provider, even a deactivated one, so payments already in flight still complete.
- **Evidence, not assumptions.** A successful connection test does not imply payments, webhooks or refunds work: the detail view shows separate evidence flags (authenticated, webhook received, payment captured, refund made) taken from real records.
- **Defaults applied (not asked):** credentials are editable only by `MANAGE_BILLING` and every change is audited without values; Razorpay's environment must match its key prefix (rzp_test_ or rzp_live_); saved-card tokens (Payment methods) stay Razorpay-only; routing uses currency and method only (country and transaction type are in the descriptor but not yet used to choose); no automatic fail-over to another gateway after a failed payment; existing Razorpay installations stay active and default after the migration.
**Still Not specified:** which provider follows Razorpay and when; routing by country, amount or cost; automatic fail-over; recurring charges through a provider (needs each provider's token or mandate flow).
**Built (2026-10-14):** requirement [REQ-BIL-003](../../02-requirements/FRD/payment-gateways/requirement.md) and its FRD ([business rules](../../02-requirements/FRD/payment-gateways/business-rules.md), [workflow](../../02-requirements/FRD/payment-gateways/workflow.md), [acceptance criteria](../../02-requirements/FRD/payment-gateways/acceptance-criteria.md)), API [payment-gateways.md](../../06-api/api-requirements/payment-gateways.md), screen [admin-payment-gateway.md](../../05-ui/screen-requirements/admin-payment-gateway.md), data model [billing-payments.md](../../07-database/data-model/billing-payments.md#c98-changes-migration-v038), integration guide [payment-gateways.md](../../09-integrations/payment-gateways.md), test cases [TC-BIL-071 to TC-BIL-106](../../../test-cases/functional/payment-gateways/TESTPLAN-BIL-003.md).
