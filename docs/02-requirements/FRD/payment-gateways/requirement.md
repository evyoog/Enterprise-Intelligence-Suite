## Summary
The Platform Admin page `/admin/billing/payment-gateway` ("Payment Gateways") manages every payment provider EIS can collect payments through. It no longer assumes Razorpay. Providers are adapters behind one backend interface; the page is driven by what the provider registry and the database say. Credentials, environment, payment methods, webhook status and validation are per gateway. Several gateways can be active at once and one can be the default.

Since [C99](../../../01-business/roadmap/open-decisions.md#c99) a platform administrator can also **add any gateway from the page** (name, currencies, methods and the credentials it needs, with the credential values stored encrypted). EIS has no payment integration for a gateway added this way, so it is **configuration only**: it can store configuration and credentials, be edited and be removed, but it is never tested, activated, routed to or used for a payment until a developer writes an adapter for it. There is no "Planned" state any more: a provider is either a working integration (Razorpay) or an administrator-added, configuration-only gateway. Stripe, PayPal, PayU and Cashfree exist only as **templates** that pre-fill the Add form.

## Functional requirements
| ID | Requirement | Priority |
|---|---|---|
| REQ-BIL-003.1 | The page shows an overview (registered, configured, active, needing configuration) and the list of gateways, all from backend data. Each row shows provider, supported methods and currencies, environment, configuration status, connection status, activation status, default marker, last test result and only the actions valid for its state. | Must |
| REQ-BIL-003.2 | A provider registry holds, per provider: id, name, description, logo key, countries, currencies, methods, transaction types, test and live support, webhook, refund and recurring support, configuration fields, setup steps and implementation status (IMPLEMENTED, a working adapter exists, or CONFIGURATION_ONLY, added by an administrator and with no adapter). Adding an adapter adds a row to the page with no UI change; gateways added by administrators are read from the database. | Must |
| REQ-BIL-003.3 | A gateway without a payment integration (CONFIGURATION_ONLY) can be configured, edited and removed, and its description and fields viewed, but it cannot be tested, activated, made default or have its methods switched (refused with 409), and is never shown as operational, counted as active or implemented, or routed to. No provider is listed as "planned": Stripe, PayPal, PayU and Cashfree are not listed unless an administrator adds them. | Must |
| REQ-BIL-003.4 | Configure shows a form built from the provider's field list (secret fields are write-only, a blank value keeps the stored one). The API never returns a secret; it returns, per field, whether it is set, its source (stored or environment) and a masked public identifier. | Must |
| REQ-BIL-003.5 | Credentials are encrypted at rest with a master key from the environment. If the key is missing, saving is refused with a clear message. Credentials are never logged, audited or committed. | Must |
| REQ-BIL-003.6 | Test connection calls the real provider with the stored credentials and shows the actual outcome: not configured, configuration incomplete, connection successful, authentication failed, provider unavailable, unsupported configuration, or test failed. The result is stored with the configuration version it tested. | Must |
| REQ-BIL-003.7 | Configured, Connected, Active and Default are separate statuses. A gateway can be activated only when its configuration is complete and a live test of the current configuration passes. Deactivate is always allowed. A default must be active; deactivating the default clears it. | Must |
| REQ-BIL-003.8 | Changing the credentials of an active gateway re-tests it in the same request; if the test fails the change is not saved. | Must |
| REQ-BIL-003.9 | Evidence flags are shown separately from the connection test: authenticated, webhook signature seen, payment captured, refund made. | Should |
| REQ-BIL-003.10 | Webhooks: `POST /webhooks/{provider}`; the provider's adapter verifies the signature on the raw body; an invalid signature is rejected and counted; events are idempotent per provider and event id; accepted for any configured provider even if deactivated. The page shows the endpoint (from `app.backend-url`), the provider's setup steps, the last event and recent failures. | Must |
| REQ-BIL-003.11 | Payment methods: per gateway, the administrator can switch off methods the provider supports; unsupported methods are never offered. Checkout shows only methods that an eligible gateway offers and Billing settings allows. | Must |
| REQ-BIL-003.12 | Routing: for each new payment the backend selects an eligible gateway (active, configured, supports the invoice currency and the chosen method; default first). With none, the payment is refused with a clear error. The frontend never selects a gateway. | Must |
| REQ-BIL-003.13 | A payment records its provider. Confirm, reconcile and refund use the payment's own provider. Changing activation or the default never changes existing payments, refunds or subscriptions. | Must |
| REQ-BIL-003.14 | Existing Razorpay behaviour, history, routes and permissions keep working. Razorpay credentials in the secrets file are still used unless a stored value exists. After migration Razorpay stays active and default. | Must |
| REQ-BIL-003.15 | Every administrator change (add, edit definition, remove, configure, rotate, test, activate, deactivate, default, methods) is audited with the actor and the gateway, never the values. | Must |
| REQ-BIL-003.16 | **Add a gateway ([C99](../../../01-business/roadmap/open-decisions.md#c99)).** A platform administrator (`MANAGE_BILLING`) adds any gateway with an **Add payment gateway** form on the page: name, code (2 to 30 characters A-Z, 0-9, underscore, starting with a letter; not `DEFAULT`, `ACTIVE`, `SUMMARY` or `TEMPLATES`, not a built-in adapter code, not an existing code: 409), description, environment (Test or Live), currencies (at least one, three letters), countries (optional, two letters), payment methods (at least one of card, upi, netbanking, wallet, bank_transfer, paypal), 1 to 12 credential fields (name of letters and digits, label, secret yes or no, required yes or no, at least one required) and optional credential values. The form can start from a template (Stripe, PayPal, PayU, Cashfree; a template already on screen is left out) whose every value can be changed. The definition can be edited later (stored values of a removed field are dropped) and the gateway removed with its stored credentials (a built-in provider cannot be edited or removed). **Credential values are checked against the fields and stored AES-256-GCM encrypted in the database** with the master key of REQ-BIL-003.5 (without the key saving is refused, 409), never returned by any API and never audited; the non-secret definition is stored separately as JSON (migration V039). | Must |
| REQ-BIL-003.17 | **Configuration-only gateways are never operational ([C99](../../../01-business/roadmap/open-decisions.md#c99)).** A gateway added by an administrator has no adapter, so EIS never routes a payment to it, never takes a payment through it and offers no webhook endpoint for it (a webhook is 404). It is labelled **"No payment integration"** in the list and details; its configuration status (Not configured, Incomplete, Configured) comes from its credentials, its connection status is always Not tested, and it is counted as registered and, when not Configured, as needing configuration, but never as implemented or active. Making it take payments needs a developer-written adapter ([09-integrations/payment-gateways.md](../../../09-integrations/payment-gateways.md#how-to-turn-an-added-gateway-into-a-real-integration)); until then it is configuration only. | Must |

## Out of scope
A payment integration (adapter) for any gateway other than Razorpay, including Stripe, PayPal, PayU and Cashfree and every gateway an administrator adds (the Add form stores configuration only; a developer writes the adapter); testing, activating or taking payments through an added gateway; routing by country, amount or cost; automatic fail-over; recurring charges through a provider; saved-card tokens for any provider other than Razorpay.
