# Business rules — Payment gateways (REQ-BIL-003)

Decision: [C98](../../../01-business/roadmap/open-decisions.md#c98) (product owner, 2026-10-14), amended by [C99](../../../01-business/roadmap/open-decisions.md#c99) (BR-1, BR-2, BR-12, BR-18, BR-19 and the new BR-20 to BR-25). Rules that apply to every payment (card data, tax, refunds) stay in [billing-payments](../billing-payments/business-rules.md); BR-21 there (one active gateway, C97) is replaced by BR-5 to BR-11 below. [BR-SEC-001](../../../03-business-rules/BR-SEC-001-central-secrets-file.md) rule 5 ("secrets are never typed on a screen") is changed **for this feature only**, by BR-3 to BR-5 below; every other secret in EIS still lives only in the common secrets file.

| ID | Rule | Enforced in |
|---|---|---|
| BR-1 | **Registry; only real integrations are operational.** Every provider EIS lists is described by a registry entry (code, name, description, logo key, countries, currencies, payment methods, transaction types, environments, webhook / refund / recurring support, configuration fields, setup steps, webhook events, implementation status). A provider is **IMPLEMENTED** only when a backend adapter (a `PaymentGateway` Spring bean) exists for it; today that is **Razorpay** only. A gateway an administrator added (BR-20) has **no adapter** and is **CONFIGURATION_ONLY**: see BR-23. **There is no "planned" provider** ([C99](../../../01-business/roadmap/open-decisions.md#c99) removed it): Stripe, PayPal, PayU and Cashfree are not listed and are only templates for the Add form (BR-25). Nothing is simulated: a connection test or a payment is always a real call to the provider, and a gateway without an adapter never reaches one. | Backend: `GatewayRegistry`, `GatewayTemplates`, `GatewayManagementService.requireImplemented` |
| BR-2 | **The page is driven by data.** The list, the overview counts, the configure form and the details are produced from the registry and the `payment_gateway_config` table. Adding a provider means adding an adapter bean; it adds a row, a form and a details view with no change to the screen or the API. A gateway an administrator adds is read from the database and is listed the same way (BR-20). A logo key the screen does not know shows a neutral monogram. | Backend: `GatewayManagementService`; frontend: `PaymentGatewayManagement`, `GatewayConfigureDialog`, `GatewayDetailsDialog`, `GatewayFormDialog` |
| BR-3 | **Credentials are encrypted at rest.** Credentials an administrator enters are stored as one AES-256-GCM ciphertext (random 12-byte IV per write, 128-bit tag) in `payment_gateway_config.credentials_encrypted`. The master key is the environment variable `PAYMENT_GATEWAY_ENCRYPTION_KEY` (base64 of exactly 32 bytes); it is never stored in the database or in source control. A key that is missing, not base64 or not 32 bytes counts as **no key**. **Without a usable key, saving any credential value is refused** (409 `INVALID_STATE`, "Credentials cannot be stored because the encryption key is not configured on the server"); saving only the environment is still allowed. If the key later changes, the stored ciphertext cannot be read: it is treated as no stored value, the details say the credentials are unreadable, and the administrator enters them again. | Backend: `CredentialCipher`, `GatewayCredentialStore`, `GatewayManagementService.saveConfiguration` |
| BR-4 | **Credentials are write-only.** No API response, log line, audit entry or screen shows a secret. For each configuration field the API returns only whether it is set, its source (`STORED`, `ENVIRONMENT` or `NONE`) and, for a **non-secret** identifier only, a masked form (for example `rzp_test_••••••7890`); a secret field never returns even a masked form. In the configure form a blank field **keeps** the stored value; only fields the administrator typed are sent. A submitted value is trimmed, must be at most 500 characters and must contain no control character; an unknown field name or an environment the provider does not offer is a 400. | Backend: `GatewayManagementService.detail`, `.saveConfiguration`; frontend: `GatewayConfigureDialog` |
| BR-5 | **Stored values win over the environment.** The credentials in force for a provider are what the deployment supplies through the environment or the common secrets file, **overridden field by field by any stored value**. Razorpay credentials already in `config/secrets.env` therefore keep working with no action; entering a value on the screen replaces that field only. The detail shows the source of each field so the administrator knows which one is in force. Whether a provider is **configured** is decided on the credentials in force. | Backend: `GatewayManagementService.resolved`, `RazorpayProperties` |
| BR-6 | **Four separate statuses.** *Configured* (every required field is set: Not configured, Configuration incomplete or Configured), *Connected* (the outcome of the last connection test **of the current configuration version**), *Active* (accepting new payments) and *Default* (the gateway tried first) are four independent facts and are never merged into one label. Connected is "Not tested" when the configuration changed since the last test (every save increments `config_version`; a test result counts only for the version it tested). A gateway that is not fully configured shows its configuration status in place of a connection status. A successful connection test does not activate a gateway and activating does not make it default (except BR-8). | Backend: `GatewayManagementService.toGateway`; frontend: `PaymentGatewayManagement` |
| BR-7 | **Connection test.** Test connection calls the real provider with the credentials in force and records and shows the actual outcome: `CONNECTION_SUCCESSFUL`, `AUTHENTICATION_FAILED` (HTTP 401 or 403 from the provider), `PROVIDER_UNAVAILABLE` (unreachable or HTTP 5xx), `UNSUPPORTED_CONFIGURATION` (the configuration cannot work, for example BR-14), `TEST_FAILED` (any other failure). With no field set it answers `NOT_CONFIGURED`, with some required field missing `CONFIGURATION_INCOMPLETE`, **without calling the provider and without storing a result**. A stored result carries the time and the configuration version tested. A provider outage is reported as such and never as bad credentials. | Backend: `GatewayManagementService.test`, `PaymentGateway.testConnection` |
| BR-8 | **Activation and default.** A gateway can be activated only when its configuration is complete (otherwise 409 "… is not fully configured yet") **and** a connection test run inside the activation request passes; a failing test leaves the gateway inactive, stores the real status and answers 409 "… was not activated: …". Several gateways can be active at once. **Deactivate** is always allowed and also clears the default. A **default must be active** (409 otherwise); making one gateway the default clears the previous default. The first gateway to be activated becomes the default when no other active gateway is the default. Deactivating or changing the default never changes an existing payment, refund or subscription. | Backend: `GatewayManagementService.activate`, `.deactivate`, `.setDefault` |
| BR-9 | **Rotating an active gateway tests first.** Saving the credentials or environment of an **active** gateway re-tests the new configuration inside the same transaction. If the test does not pass, nothing is saved (credentials, environment and version stay as they were), the gateway stays active on the old credentials, the response is 409 "Not saved: {status}: {message} The previous configuration is unchanged." and `PAYMENT_GATEWAY_CONFIGURATION_REJECTED` is audited without values. If it passes, the new configuration and its passing result are saved together. Saving an **inactive** gateway needs no test: it is saved, the version increases and Connected becomes "Not tested". | Backend: `GatewayManagementService.saveConfiguration` |
| BR-10 | **Routing.** The backend, never the browser, chooses the gateway for every **new** payment. A gateway is eligible when it is implemented, **active**, **fully configured**, lists the invoice's currency, and (when the customer chose a method) has that method switched on. Eligible gateways are ordered **default first**, then by provider code; the first is used. With none, the payment is not started and the customer gets 503 `PAYMENT_GATEWAY_NOT_CONFIGURED` "No payment gateway is available for {currency} {method} payments." Routing uses **currency and method only**: the country and transaction type in the registry entry are descriptive and are not used to choose, and there is **no automatic fail-over** to another gateway after a provider error. | Backend: `GatewayRoutingService` |
| BR-11 | **A payment keeps its provider.** The payment row records the provider that created it. Confirming, reconciling and refunding that payment always go to **that provider**, whatever is active or default now, and need only that the provider's credentials are still complete (503 otherwise). A refund of an OFFLINE payment is refused as before. Changing the default, deactivating a gateway or removing a method never alters a payment that exists. | Backend: `PaymentService`, `GatewayRoutingService.forProvider` |
| BR-12 | **Webhooks: endpoint and signature.** Each implemented provider has one endpoint, `POST /webhooks/{provider}` (the provider code in lower case; `/webhooks/razorpay` is unchanged). It needs no user token and is trusted **only** through the provider's own signature, which the provider's adapter verifies against the **raw request body** (never a re-serialised one). A provider that is unknown, or is a gateway added by an administrator (no adapter, BR-23), is 404. A provider that is not fully configured, a signature that does not verify, a missing signature header and a body the adapter cannot understand are each 400 `SIGNATURE_INVALID`, change nothing, and are counted (BR-13). The webhook URL shown on screen is `app.backend-url` (environment variable `BACKEND_URL`) plus `/webhooks/{provider}`; when that address points at the local machine the screen warns that the provider cannot reach it. | Backend: `PaymentWebhookController`, `PaymentService.processWebhook`, adapter `verifyWebhook` and `parseWebhook` |
| BR-13 | **Webhooks: idempotency, deactivated providers and failure tracking.** An event is processed at most once **per provider and event id** (migration V038: unique on `provider` and `provider_event_id`, so the same id from two providers is two events); a repeat, including one that races a first delivery, is acknowledged with 200 and changes nothing. Events are accepted for **any configured provider, even a deactivated one**, so a payment already in flight still completes. A captured or failed event changes a payment only if that payment belongs to the same provider and order id, and never changes an already CAPTURED payment; a payment already captured is not paid twice. Event types that are not subscribed are stored and otherwise ignored; `refund.processed` is recorded only (refunds made from the admin screen already update the payment). **Failures are one counter and the latest reason on the gateway row** (`webhook_failure_count`, `last_webhook_failure_at`, `last_webhook_failure_reason`, 300 characters), **not a row per attempt**, so an unauthenticated caller cannot grow the database; the counter is not reset by a later success. A correctly signed accepted event sets `last_webhook_at` and the event type, and the signature status becomes "Verified". | Backend: `PaymentService.processWebhook`, `GatewayManagementService.recordWebhookReceived`, `.recordWebhookFailure`; database: `uq_payment_webhook_event_provider` |
| BR-14 | **Razorpay environment and key prefix.** Razorpay has the environments Test and Live. The Key ID must start with `rzp_test_` or `rzp_live_`, and a `rzp_test_` key requires environment Test, a `rzp_live_` key requires Live; a mismatch, or any other prefix, is refused with 400 when saved and reported as `UNSUPPORTED_CONFIGURATION` when tested. A Razorpay configuration that predates this feature has no environment chosen yet and is accepted as it is until one is chosen. | Backend: `RazorpayGateway.validateConfiguration` |
| BR-15 | **Payment methods.** Each gateway offers the methods its registry entry lists (Razorpay: card, UPI, netbanking, wallet). An administrator can switch off methods per gateway; at least one must stay on, and a method the provider does not support is refused (400). By default every supported method is on. The methods checkout offers for an invoice are the methods Billing settings allow **and** that at least one eligible gateway offers for the invoice's currency; start-payment refuses a method Billing settings switched off (400, as in C60). | Backend: `GatewayManagementService.setMethods`, `GatewayRoutingService.offeredMethods`, `CheckoutService` |
| BR-16 | **Evidence, not assumptions.** The details show four separate evidence flags taken from real records: *authenticated* (the current connection status is successful), *webhook received* (a correctly signed webhook has been accepted), *payment captured* (a CAPTURED payment of that provider exists) and *refund made* (a payment of that provider has a refunded amount). A passing connection test never sets the last three. | Backend: `GatewayManagementService.detail` |
| BR-17 | **Existing Razorpay installations keep working.** Migration V038 inserts the Razorpay row as **active and default**; if the row is missing it is created the same way on first use. Razorpay credentials in the secrets file keep working (BR-5), and the existing routes, the `/webhooks/razorpay` URL, payment history, refunds and permissions are unchanged. The earlier endpoints `GET /admin/billing/gateway` and `POST /admin/billing/gateway/test` still answer for Razorpay, and `PUT /admin/billing/gateways/active` is kept as an alias of `PUT /admin/billing/gateways/default`. `billing_settings.active_gateway` (V037) is **no longer used** by routing. Saved-card tokens (Payment methods) stay **Razorpay-only**. | Database: V038; backend: `GatewayManagementService.configOf`, `AdminBillingController`, `AdminPaymentGatewayController` |
| BR-18 | **Permissions.** Every endpoint under `/admin/billing/**`, including `/admin/billing/gateways/**` (also add, edit definition, remove and templates, BR-20 to BR-25), needs the platform permission `MANAGE_BILLING`: no token is 401, a signed-in user without it is 403. Only `MANAGE_BILLING` can add, edit or remove a gateway and enter, replace or rotate credentials. The webhook endpoint is the only public one, and it is limited by BR-12. | Backend: `SecurityConfig` |
| BR-19 | **Audit.** Every administrator change is audited with the actor and the gateway and **never a value**: `PAYMENT_GATEWAY_CONFIGURED` (names the fields changed and the environment, not their values), `PAYMENT_GATEWAY_CONFIGURATION_REJECTED` (a rotation refused by BR-9, with the failing status), `PAYMENT_GATEWAY_TESTED` (with the outcome), `PAYMENT_GATEWAY_ACTIVATED`, `PAYMENT_GATEWAY_DEACTIVATED`, `PAYMENT_GATEWAY_DEFAULT_CHANGED`, `PAYMENT_GATEWAY_METHODS_CHANGED`, and since C99 `PAYMENT_GATEWAY_ADDED` (names the credential fields stored, not their values), `PAYMENT_GATEWAY_DEFINITION_CHANGED` and `PAYMENT_GATEWAY_REMOVED`. The details list the ten most recent of these (target type `PaymentGateway`, target id the provider code). Webhook deliveries are not audit entries: they are the `payment_webhook_event` rows and the counters of BR-13. | Backend: `GatewayManagementService`, `AuditService` |
| BR-20 | **An administrator adds any gateway.** A platform administrator with `MANAGE_BILLING` adds a gateway with `POST /admin/billing/gateways` (the **Add payment gateway** form). Required: name (up to 100 characters), code, at least one currency, at least one payment method and 1 to 12 credential fields. Optional: description (up to 300 characters), logo key, countries, environment (TEST or LIVE, default TEST) and the credential values. **Code:** 2 to 30 characters, capital letters, digits and underscore, starting with a letter (input is upper-cased); `DEFAULT`, `ACTIVE`, `SUMMARY` and `TEMPLATES` are reserved because they are fixed paths under `/admin/billing/gateways`; the code cannot equal the code of a built-in adapter or of a gateway that already exists (HTTP 409 "A payment gateway with the code {CODE} already exists."), and cannot be changed later. **Currencies:** up to 20 three-letter codes (upper-cased). **Countries:** up to 50 two-letter codes. **Methods:** any of card, upi, netbanking, wallet, bank_transfer, paypal. **Credential field:** a name of letters and digits starting with a letter (up to 40, unique ignoring case), a label (up to 60), secret yes or no, required yes or no; at least one field is required. A request that breaks any rule is a 400 with the reason and **saves nothing**. A successful add answers 201 with the gateway details; it is **inactive, never default** and is audited as `PAYMENT_GATEWAY_ADDED`. | Backend: `GatewayManagementService.create`, `.validatedDefinition`; frontend: `GatewayFormDialog` |
| BR-21 | **The definition is data, kept without secrets.** The definition (description, logo, countries, currencies, methods, environments Test and Live, credential field list) is stored as JSON in `payment_gateway_config.definition`, with the flag `custom` and the name in `display_name` (migration V039). It never holds a credential value. **Edit definition** (`PUT /admin/billing/gateways/{code}/definition`) is allowed only for an added gateway: the code cannot change; the name, description, countries, currencies, methods and field list can. Stored values of a field that is **removed** are dropped (deleted from the ciphertext); values of the fields kept are unchanged; a field's secret or required flag may change; payment-method switches are reset (all methods on); the configuration version increases; the audit action is `PAYMENT_GATEWAY_DEFINITION_CHANGED`. The screen does not rename an existing credential name (its input is disabled), so renaming means removing the field and adding another. | Backend: `GatewayManagementService.updateDefinition`, `GatewayRegistry`; database: V039 |
| BR-22 | **Credentials of an added gateway.** The values sent with the add request, and later with `PUT …/{code}/configuration`, follow BR-3 to BR-5 exactly: each is trimmed, at most 500 characters, no control character, and must belong to a field of the gateway's definition (otherwise 400 "Unknown field: …"); a blank value is ignored and keeps the stored one. They are stored **AES-256-GCM encrypted** in `payment_gateway_config.credentials_encrypted`; **without a usable `PAYMENT_GATEWAY_ENCRYPTION_KEY` an add or a save that contains any value is refused** (409 "Credentials cannot be stored because the encryption key is not configured on the server (PAYMENT_GATEWAY_ENCRYPTION_KEY).") and nothing is saved; an add with no values needs no key. **No API response, log line or audit entry carries a value:** the details show for each field only whether it is set and its source (`STORED`), and, for a non-secret field, a masked form (first four and last four characters around bullets; a value of 8 characters or fewer shows only bullets); a secret field never shows even a mask. Saving an added gateway's configuration increases the version and needs **no connection test** (there is nothing to test, BR-23). | Backend: `GatewayManagementService.create`, `.saveConfiguration`, `.cleanValues`, `.detail`, `CredentialCipher` |
| BR-23 | **A gateway added by an administrator is configuration only; it is never operational.** EIS has **no adapter** for it (implementation `CONFIGURATION_ONLY`, shown as "No payment integration"). It can store configuration and credentials, be configured, edited and removed. **Test connection, Activate, Deactivate, Make default and switching payment methods are refused** with 409 `INVALID_STATE` "{name} has no payment integration in EIS, so it can store credentials but cannot be tested, activated or used for payments."; the row offers none of those buttons (`actions.test`, `activate`, `deactivate`, `setDefault` are false). It is **never routed to** (BR-10), never takes or confirms a payment, and has **no webhook endpoint**: `POST /webhooks/{code}` is 404 and is not counted. Its **configuration status** is computed from its credentials as for any provider (Not configured, Configuration incomplete, Configured: every required field set); its **connection status** is always Not tested, with the message "No payment integration exists for this gateway, so it cannot be tested or activated."; it is never Active or Default. In the overview **Registered** counts it, **Configured** counts it when Configured, **Needs configuration** counts it when it is not Configured, and **Implemented** and **Active** never count it. **Honest limit:** to make an added gateway take payments a developer must write an adapter for it (the `PaymentGateway` interface, [09-integrations/payment-gateways.md](../../../09-integrations/payment-gateways.md#how-to-turn-an-added-gateway-into-a-real-integration)); once an adapter with the same code exists, the adapter takes over the code (the registry no longer lists the added definition, the gateway is IMPLEMENTED and can no longer be edited or removed from the screen), and the stored credentials and environment of the added row are reused (a stored value whose name the adapter does not declare is ignored). | Backend: `GatewayManagementService.requireImplemented`, `.toGateway`, `.summary`, `GatewayRoutingService`, `GatewayRegistry.descriptors`, `PaymentService.processWebhook` |
| BR-24 | **Remove.** `DELETE /admin/billing/gateways/{code}` (204) deletes an added gateway and its stored credentials. The screen asks for a confirmation ("Remove {name}?": the gateway and its stored credentials are deleted, this cannot be undone). A **built-in provider** (Razorpay, or any code an adapter owns) cannot be edited or removed: 409 "{name} is a built-in provider; its definition cannot be changed or removed." An unknown code is 404. An added gateway can never have taken a payment (BR-23), so no payment, refund or subscription is affected; its audit entries (`PAYMENT_GATEWAY_ADDED` and the rest) remain. The code can be added again afterwards. | Backend: `GatewayManagementService.delete`, `.requireCustom` |
| BR-25 | **Templates are starting points, not gateways.** `GET /admin/billing/gateways/templates` returns pre-filled definitions (name, description, logo key, countries, currencies, methods, credential fields, never values) for **Stripe, PayPal, PayU and Cashfree**. A template is not listed on the page, is not routed to and has no status; choosing it in the Add form only fills the form, every value of which can be changed, and the result is an ordinary added gateway (BR-20 to BR-23). A template whose code is already on the page (added, or a built-in provider) is omitted from the list. | Backend: `GatewayTemplates`, `GatewayManagementService.templates`; frontend: `GatewayFormDialog` |

## C99: gateways added by an administrator
BR-20 to BR-25 above are the C99 rules: add, definition, credentials, configuration-only, remove, templates.

## Not specified
Which provider follows Razorpay and when; routing by country, amount or cost; automatic fail-over to another gateway; recurring charges through a provider (each provider's token or mandate flow); saved-card tokens for any provider but Razorpay; which gateway gets a real integration (adapter) after Razorpay and when; how an administrator could switch an added gateway to a real integration without a developer (it cannot be done from the screen). They are recorded under [C98](../../../01-business/roadmap/open-decisions.md#c98) and must not be built until decided.
