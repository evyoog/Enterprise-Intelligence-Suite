# Business rules — My profile

Every rule is enforced on the server; the screen mirrors the validation rules (BR-PRF-023). Field errors are keyed `<section>.<field>` (BR-PRF-012). Defaults the owner did not state are marked in [C107](../../../01-business/roadmap/open-decisions.md#c107) (PF-1 to PF-14).

| ID | Rule |
|---|---|
| BR-PRF-001 | **Own profile only.** `/me/profile` and its photo belong to the signed-in person, resolved from the sign-in token. No customer id is accepted in the path, query or body. Every signed-in role (platform administrator, organization administrator, member, individual) may read and edit their own profile with no extra permission. An unauthenticated call is refused (401). An API key is not a person and is refused (403). Another person's profile or photo is never readable or writable through `/me/**`. A "platform administrator" for profile purposes is a person who holds the platform permission `MANAGE_REGISTRATIONS` (the same one that guards the admin registration endpoints). |
| BR-PRF-002 | **No record.** A signed-in person who is not a platform administrator and has no customer record gets 404 on `GET` and `PUT /me/profile` and on every photo call. A platform administrator with no record gets a profile with `exists=false`, built from the token (email, given name, family name), all other fields empty and completion 0 of 11 with every item missing. `GET /me/profile/completion` is never 404: for any signed-in person without a record it answers 200 `{exists:false, percent:0, filled:0, total:11, missing:[all 11 keys]}`. |
| BR-PRF-003 | **Creating the platform administrator's own record is optional.** Nothing forces it and nothing is blocked without it. The first valid `PUT /me/profile` of a platform administrator with no record creates the customer row (email from the token, the sign-in linked to the row, status COMPLETED) and is audited `PROFILE_CREATED`. The token must carry an email (400 without). If any customer row already has that email (compared without regard to letter case, so it belongs to a different login), the call is refused with 409 and nothing is created. Keycloak is updated at creation only if the names typed differ from the token's given and family name (BR-PRF-015). A non-administrator with no record cannot create one this way (404, BR-PRF-002). |
| BR-PRF-004 | **Email, role and status are read-only.** The update request has no email, role, status or photo field. The email shown is the login name and never changes through the profile. |
| BR-PRF-005 | **Normalisation of text.** Every text value is trimmed and its inner runs of whitespace are collapsed to one space. A blank value becomes null (the field is cleared); a blank required field (first name, last name) is an error. A tab, line feed or carriage return counts as whitespace and is collapsed, so a bio is stored as one paragraph. URLs are trimmed but not rewritten and may not contain spaces. |
| BR-PRF-006 | **Forbidden characters.** Every free-text field (names, bio, job title, department, company, industry, address, city, state, postal code, country, URLs) refuses control characters (other than tab, line feed and carriage return, see BR-PRF-005) and the characters `<` and `>`, with a field error. |
| BR-PRF-007 | **Names.** First name and last name are required, 1 to 100 characters, matching `^[\p{L}\p{M}][\p{L}\p{M} .'’-]{0,99}$` (letters and marks, then letters, marks, space, full stop, apostrophe, right single quote and hyphen). Preferred name is optional, at most 60 characters, same pattern. |
| BR-PRF-008 | **Phones.** Mobile and alternate phone are optional. Spaces, hyphens, dots and parentheses are removed; the result must match `^\+[1-9]\d{6,14}$` (a plus sign, a country code not starting with 0, 7 to 15 digits in all) and is stored in that normalised form. Anything else is a field error. The value typed (before the separators are removed) may be at most 40 characters. |
| BR-PRF-009 | **Bio and work.** Bio is optional, at most 500 characters. Job title at most 100, department at most 100, company name at most 150, industry at most 100 (industry is free text, PF-13). All optional. |
| BR-PRF-010 | **Address.** Address line 1 and 2 at most 150, city at most 80, state at most 80, country at most 80 (free text, PF-13), postal code matching `^[A-Za-z0-9][A-Za-z0-9 -]{1,10}$` (2 to 11 characters, so the pattern is the effective limit although the column holds 12). When the country is India (`India` or `IN`, in any letter case) the postal code must be exactly 6 digits. All optional. |
| BR-PRF-011 | **Online.** LinkedIn URL: `https` only, host `linkedin.com` or a subdomain of it, at most 200 characters. Website URL: `http` or `https`, a valid host, at most 200 characters. A valid host is a domain name with a top-level domain (not an IP address, not `localhost`, not a Unicode host name: an international name must be written in its ASCII `xn--` form) and no user name or password in the address. Both optional. |
| BR-PRF-012 | **Saving.** `PUT /me/profile` replaces the four sections as a whole: a field that is blank or left out is cleared. The save is all or nothing: when any field is invalid nothing is stored and the answer is 400 `{status, message: "Validation failed", fieldErrors}` with **every** invalid field in one answer, keyed `<section>.<field>` (for example `personal.firstName`, `address.postalCode`) with an English message. A successful save that changes at least one value sets `profile_updated_at` and returns the full profile; a save that changes nothing stores nothing, writes no audit entry and calls no other system. |
| BR-PRF-013 | **Photo file.** Only `image/jpeg`, `image/png` and `image/webp` are accepted; SVG and every other type are refused. The size is at most 1 MB (1,048,576 bytes); an empty file is refused. The declared type must be one of the three and must equal the type found from the file's first bytes; the file name is ignored. The image must be at most 4096 x 4096 pixels; JPEG and PNG are fully decoded (a damaged file is refused), a WebP is checked by its container header and declared size only (the Java runtime has no WebP decoder). A wrong type or content is 400; too large is 413. The browser shrinks the image to 512 x 512 before upload. |
| BR-PRF-014 | **Photo storage and reading.** One photo per customer in `customer_photo` (replaced on upload, deleted on remove, deleted with the customer). Removing when there is none is not an error. A person with no record cannot add or remove a photo (`PUT` and `DELETE /me/profile/photo`): 404, or 409 "Create your profile before adding a photo" for a platform administrator. The stored `Content-Type` is the one detected from the first bytes. `GET /me/profile/photo` returns the stored bytes with the stored `Content-Type`, `Cache-Control: private, max-age=0, must-revalidate`, an `ETag` and `X-Content-Type-Options: nosniff`, and answers 304 when `If-None-Match` equals the `ETag`; 404 when there is none. The photo is never part of the customer entity or the profile JSON (only `photo.present` and `photo.updatedAt`). |
| BR-PRF-015 | **Names mirror to Keycloak.** When the first or last name changes, the Keycloak user is updated with the new names in the same save. If Keycloak refuses or cannot be reached, the whole save is rolled back (no field changes, no audit entry) and the answer is 502. When neither name really changes (after normalisation), or the customer has no Keycloak link, Keycloak is not called; a change of any other field never calls it. First and last name stay non-blank because the realm refuses sign-in without them. |
| BR-PRF-016 | **Names owned by an external identity provider.** `account.nameEditable` tells the screen whether the person's names may be edited; when false the screen shows the two names read-only. In this version `FederatedAccountService` writes the names only when it first creates an account from a SAML or OIDC sign-in and never overwrites them on later sign-ins, so no sign-in method owns the names and `nameEditable` is true for every person. The field exists so it can be turned off; server-side refusal of a name change (a field error) is to be added together with the first rule that makes it false, because nothing makes it false today. |
| BR-PRF-017 | **Completion.** 11 equally weighted items: photo, mobile, job title, department, company name, industry, address line 1, city, state, postal code, country. An item counts when its value is not blank (the photo counts when a `customer_photo` row exists). `percent = round(filled * 100 / 11)` (half up), `total = 11`, `missing` lists the keys not filled in the order above. One shared computation serves the profile response and `GET /me/profile/completion` (`{exists, percent, filled, total, missing}`). |
| BR-PRF-018 | **Two completion measures.** The profile's completion (BR-PRF-017) and the directory's (BR-DIR-004/005, five items for an individual) are different sets and may show different percentages for the same person. The directory computation is unchanged by this feature; aligning them is a follow-up. |
| BR-PRF-019 | **Global bar.** Shown below the app bar on every page of the signed-in tool when the profile `exists` and `percent` is below 100. Hidden at 100, when `exists` is false, and on `/account/profile`. The person can dismiss it; the dismissal is kept per user in the browser session storage (it survives page changes and reloads, and ends when the browser session ends, so the bar returns at the next sign-in in a new browser session; signing out and in again in the same tab does not clear it; another person signing in on the same tab does not inherit it). It reloads `GET /me/profile/completion` after a profile save and after a photo upload or removal, and does not poll. |
| BR-PRF-020 | **Platform administrator edits a customer.** `GET` and `PUT /admin/registrations/individuals/{customerId}/profile` take and return the same bodies as `/me/profile` (same validation, normalisation, Keycloak mirroring and rollback; no photo), require `MANAGE_REGISTRATIONS`, and answer 404 for an unknown customer. They cannot create a customer. The role shown is the viewed person's own (not the administrator's). An administrator who has no customer record of their own can still edit; the audit entry then names the administrator by login. The save is audited `PROFILE_UPDATED_BY_ADMIN` with the administrator as actor and the customer as entity. A person without `MANAGE_REGISTRATIONS` (including an organization administrator) gets 403. |
| BR-PRF-021 | **Audit.** `PROFILE_CREATED`, `PROFILE_UPDATED`, `PROFILE_PHOTO_UPDATED`, `PROFILE_PHOTO_REMOVED` and `PROFILE_UPDATED_BY_ADMIN` are written through the audit service. An entry names the sections that changed (personal, work, address, online) and never contains a field value or the photo. A save or an administrator's save that changes nothing writes no entry, and a photo removal when there is no photo writes none. |
| BR-PRF-022 | **Account tab.** Read-only: email, role (`PLATFORM_ADMIN` for any holder of `MANAGE_REGISTRATIONS`, even one who also has a customer record; otherwise `ORG_ADMIN`, `MEMBER` or `INDIVIDUAL`), organization name and code, membership status (`ACTIVE`, `SUSPENDED` or `INACTIVE`; the active membership is preferred, otherwise the most recent) and member-since date (the membership's joined date; for a person with no organization the organization and status are empty and member-since is the date the account was created), and links to `/account/security`, `/account/preferences` and, for an organization administrator, People & structure (`/organization/members`) and the business dashboard. The sign-in method is not shown in this version (the API carries no such field). Language and time zone are not editable on the profile. |
| BR-PRF-023 | **Screen mirrors the server.** The screen applies BR-PRF-005 to BR-PRF-011 with shared validators before sending; the tab of an invalid field shows an error badge; a server field error is shown on its field; Save is refused locally while a field is invalid. The server stays the final check. Leaving with unsaved changes asks for confirmation; Discard restores the saved values. |
| BR-PRF-024 | **Text and accessibility.** All visible text comes from the English and Spanish files (`profile.*`, `appShell.nav.profile`, `profile.bar.*`). Every input has a label, an invalid input has `aria-invalid` and helper text, the tabs are keyboard-operable, the progress bars have an accessible name and value, and the page and bar pass the automated accessibility check. |
| BR-PRF-025 | **Profile menu.** The account menu at the top right lists **My profile** first, shows the person's email line, and its avatar and name block opens `/account/profile`. |
