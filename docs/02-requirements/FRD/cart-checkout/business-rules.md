# Business rules — Cart and checkout (REQ-MKT-003)

Cross-feature rules that also apply: [BR-BIL-001 No raw card data](../../../03-business-rules/BR-BIL-001-no-raw-card-data.md), and the billing rules in [billing-payments/business-rules.md](../billing-payments/business-rules.md).

| ID | Rule | Enforced in | Source |
|---|---|---|---|
| BR-1 | A cart belongs to exactly one signed-in user. Another user's cart or cart item is refused with a generic 404. | backend | REQ-MKT-003.2 |
| BR-2 | Only paid plans can be added. A free plan keeps its current subscribe behaviour and is refused by the add-to-cart API. | backend | REQ-MKT-003.1 |
| BR-3 | A product appears in a cart at most once. Adding another plan of a product already in the cart replaces that item's plan (to confirm in review, Open question 6). | backend (unique cart + product) | REQ-MKT-003.1 |
| BR-4 | Change plan accepts only a plan of the same product. A plan of another product is refused (400). | backend | REQ-MKT-003.4 |
| BR-5 | Each item stores the unit price and currency at the moment it was added (`unit_price_at_add`). The cart shows the current catalog price. A difference is a validation issue (BR-6 b), and the old price is never charged. | backend | REQ-MKT-003.5 |
| BR-6 | Validation runs on **Proceed to checkout / Submit order for approval**, and again when the checkout is created. It reports, per item: (a) `NOT_AVAILABLE` — the product is not `ACTIVE`, or the plan no longer exists; (b) `PRICE_CHANGED` — the current price differs from `unit_price_at_add`, and the old and new prices are returned; (c) `ALREADY_SUBSCRIBED` — the customer (or, for an organization member, the organization) has an ACTIVE subscription to the product; (d) `MISSING_DEPENDENCY` — the product depends on a product that the customer neither has an ACTIVE subscription to nor has in the same cart. (e) `CURRENCY_MISMATCH` — the item's currency differs from the cart's first item (one invoice has one currency; [C59](../../../01-business/roadmap/open-decisions.md#c59) default). | backend (frontend shows the messages) | REQ-MKT-003.5 |
| BR-7 | Checkout cannot be created while any item has an issue. A `PRICE_CHANGED` issue clears once the customer confirms the new price, which updates `unit_price_at_add`; the screen confirms **every** changed price with one action ([C100](../../../01-business/roadmap/open-decisions.md#c100) CA-6 A; the API still confirms one item per call). The other issues clear only when the item is removed or changed. | backend | REQ-MKT-003.5 |
| BR-8 | Tax lines in the cart use the region from the customer's billing details and the rules in [REQ-BIL-002](../tax-rules/requirement.md). Without billing details, no tax is calculated and the cart shows "Tax calculated at payment". The amount actually charged is the invoice's, calculated at checkout. | backend | REQ-MKT-003.3 |
| BR-9 | **Individual:** checkout creates the subscriptions (the same as today's subscribe) and **one invoice** for all of them, then empties the cart. **Organization administrator or Manage billing holder:** a direct purchase (BR-14). **Other organization member:** submitting creates one purchase request (BR-15) and empties the cart; payment happens only after an organization administrator approves it. | backend | REQ-MKT-003.8, .11 to .13 |
| BR-10 | Checkout is idempotent per cart: a second Proceed for the same cart contents (for example a double click) returns the checkout already created and never creates a second invoice or order. | backend | REQ-MKT-003.8 |
| BR-11 | Adding, changing, removing and clearing items are not audited. Order submission and payment are audited under their existing rules (to confirm in review). | backend | REQ-MKT-003.9 |
| BR-12 | No fee, shipping or quantity-stepper field exists in the cart or its API ([C100](../../../01-business/roadmap/open-decisions.md#c100) CA-7 A). A **coupon** field exists (BR-18); it replaces the earlier "no coupon" rule ([C50](../../../01-business/roadmap/open-decisions.md#c50), [C100](../../../01-business/roadmap/open-decisions.md#c100) PB-1 note). | backend / frontend | REQ-MKT-003 Out of scope |
| BR-13 | **Who buys directly** is decided on the server and returned as `continueAs`: `INDIVIDUAL` (not an organization member); `ORGANIZATION_BUYER` (an ACTIVE member who is an organization administrator or holds `MANAGE_ORGANIZATION_BILLING`); `ORGANIZATION_MEMBER` (any other ACTIVE member: the cart is a purchase request). | backend | REQ-MKT-003.8 |
| BR-14 | **Direct purchase:** creates an order recorded as APPROVED by the buyer with the note "Purchased directly", creates or reactivates every organization subscription and issues **one invoice** (with the coupon, if any) in one transaction; audit `ORDER_PURCHASED_DIRECTLY`; publishes `OrderApproved`. When the buyer is not an organization administrator every ACTIVE administrator is notified "A purchase was made for your organization" with the products. A cart whose items are all free is not a cart (BR-2), so an invoice always exists. | backend | REQ-MKT-003.13 |
| BR-15 | **Purchase request:** needs a non-blank **reason** (up to 500 characters; blank is refused with "Tell your organization admin why you need this before you submit the request." and the cart is kept). Creates **one** order (status SUBMITTED) holding every product and the reason; no subscription and no invoice yet; audit `ORDER_SUBMITTED`; every ACTIVE administrator is notified with the products and the reason; the checkout result is `ORDER` with one order id. A repeated submit within 2 minutes returns the same order (BR-10). | backend | REQ-MKT-003.12 |
| BR-16 | **Approval of a request** provisions every product and creates **one invoice**, as for a direct purchase but without a coupon ([REQ-ORD-001.10](../order-lifecycle/requirement.md)). | backend | REQ-MKT-003.11, .12 |
| BR-17 | **Seats × price:** an organization item's `seats` is the quantity of the organization's existing subscription to the product, else its licensed seats (at least the ACTIVE members, at least 1); `amount` = unit price × seats; the subtotal is the sum of the amounts. An individual item has 1 seat. The server computes this; the browser only displays it. | backend | REQ-MKT-003.17 |
| BR-18 | **Coupon in the cart:** one code per cart (`cart.coupon_code`, stored in capitals). Applying one needs a non-empty cart and is refused for a purchase request ("A coupon cannot be used on a purchase request. An organization admin can use it when they buy."), for a blank code, and for any code the coupon rules refuse ([billing-payments BR-24 to BR-28](../billing-payments/business-rules.md)). The cart's `discount` is computed from the current subtotal each time; when the code can no longer be used the cart returns `discount` 0 and a `couponMessage` and keeps the code visible. `total` = `subtotal` − `discount`. Tax is not in the cart (BR-8). Removing the code clears it. | backend | REQ-MKT-003.18 |
| BR-19 | **Checkout re-checks the coupon:** the code is checked again, and counted as redeemed, only when the invoice is created. If it no longer works the checkout fails with the reason (400), **nothing is created** (no subscription, order or invoice) and the cart is unchanged. A successful checkout clears the coupon with the cart. The coupon is never applied to a purchase request. | backend | REQ-MKT-003.18 |
| BR-20 | **Known gap (see [Open points](requirement.md#open-points)):** the server removes the coupon only when the customer removes it or checks out. **Clear cart** and removing the last item leave `cart.coupon_code` on the cart row, so it reappears when items are added again; the screen hides it while the cart is empty. | backend | REQ-MKT-003.18 |
