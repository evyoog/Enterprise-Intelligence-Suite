# Business rules — Order Lifecycle

| ID | Rule | Enforced in | Source |
|----|------|-------------|--------|
| BR-ORD-001 | Submitting an order requires an ACTIVE membership in good standing (same check as every other organization self-service action — see `OrderService#resolveMembership`). Create/Validate/Price/Submit (09.01.01.01–.04) are one call: every product must be ACTIVE and eligible, and a given `planId` must belong to its product, or the request is refused (400/404). No separate draft state exists. | backend | REQ-ORD-001.1, .2 |
| BR-ORD-002 | Approving an order requires the `MANAGE_ORDERS` organization permission (seeded to ORG_ADMIN) and refuses (400) an order that is not currently SUBMITTED. Approval calls `SubscriptionService#subscribeOrganization` (one product) or `#subscribeOrganizationItems` (several; one invoice) in the same transaction, then sets the order to APPROVED — there is no separate PROVISIONED status or async step. | backend | REQ-ORD-001.3 |
| BR-ORD-003 | Rejecting an order requires the same `MANAGE_ORDERS` permission and also refuses (400) an order that is not currently SUBMITTED. The optional note is stored on the order either way (approve or reject). | backend | REQ-ORD-001.4 |
| BR-ORD-004 | Only the order's own requester may cancel it, and only while it is still SUBMITTED (400 otherwise) — an already-decided order is a historical record, not cancellable. | backend | REQ-ORD-001.5 |
| BR-ORD-005 | Every action resolves the order and confirms it belongs to the caller's own organization, or refuses with the same 404 a nonexistent id would give. | backend | REQ-ORD-001.7 |
| BR-ORD-006 | Every decision (approve/reject) notifies the requester; every new submission notifies every ACTIVE ORG_ADMIN of the organization. Both are recorded in the audit log (`ORDER_SUBMITTED`/`_APPROVED`/`_REJECTED`/`_CANCELLED`). | backend | REQ-ORD-001.3, .4 |

Rules shared with other features belong in `docs/03-business-rules/` and are referenced here by ID.
| BR-ORD-007 | **Several products** ([C100](../../../01-business/roadmap/open-decisions.md#c100) CA-1 B). A request holds `items` (product, optional plan) or, as before, one `productId` and `planId`. At least one product is required (400 "Choose at least one product."); a product may appear once (400 "Each product can be in an order once."). The order's own `productId` and `planId` are those of the first item; every item is a row of `order_item`. An order with no item rows (made before V040) is shown and approved as one item. | backend | REQ-ORD-001.8 |
| BR-ORD-008 | **Reason.** `reason` is trimmed; blank is stored as none; more than 500 characters is refused (400 "The reason can have up to 500 characters."). The cart refuses a blank reason before it submits (REQ-MKT-003.12). The reason is returned as `requestReason` and shown to the requester and to the deciding administrator. | backend | REQ-ORD-001.9 |
| BR-ORD-009 | **Approval bills once.** Approving an order with several products provisions every product and creates **one invoice** with one line per product; a one-product order creates its single invoice as before. No coupon is applied to an approved request. Rejecting or cancelling provisions and bills nothing. | backend | REQ-ORD-001.10 |
| BR-ORD-010 | **Direct purchase.** Allowed only for an ACTIVE member who is an organization administrator or holds `MANAGE_ORGANIZATION_BILLING` (else 403). It validates the items as BR-ORD-001, creates the order already APPROVED, decided by the buyer at that moment with the note "Purchased directly", provisions every product, creates one invoice (with the buyer's coupon, if any), writes the audit entry `ORDER_PURCHASED_DIRECTLY` and publishes `OrderApproved` (with `productIds`). If the buyer is not an organization administrator, every ACTIVE administrator is notified "A purchase was made for your organization". | backend | REQ-ORD-001.11 |
| BR-ORD-011 | **Notification of a request.** A new request notifies every ACTIVE administrator: "New purchase request awaiting approval" with the requester's name, the products and the reason (BR-ORD-006). | backend | REQ-ORD-001.9 |
| BR-ORD-012 | **3-day pending reminder, once only ([C103](../../../01-business/roadmap/open-decisions.md#c103) / [REQ-TEN-010](../application-access/requirement.md)).** An order still SUBMITTED 3 or more days (`OrderService.PENDING_REMINDER_DAYS`) after creation is reminded to every ACTIVE ORG_ADMIN exactly once (`orders.reminded_at` is set on the first reminder); it is never auto-approved or auto-rejected by this reminder — only `approveOrder`/`rejectOrder` change its status. Runs hourly (`OrderReminderJob`), gated by `app.orders.job-enabled` (off in tests). | backend | REQ-TEN-010.10 |
