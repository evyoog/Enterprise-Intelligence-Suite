# Business rules — Application access requests (REQ-TEN-010)

| ID | Rule | Enforced in | Source |
|----|------|-------------|--------|
| BR-AAC-001 | **Must already be subscribed.** A member can request access only to a product whose status is ACTIVE in the catalog and for which the organization holds an ACTIVE subscription; otherwise the request is refused (400 "Your organization does not have an active subscription for {product}."). Requesting a product the organization does not subscribe to is never an access request — it is a purchase request ([REQ-ORD-001](../order-lifecycle/requirement.md)). | backend | REQ-TEN-010.1 |
| BR-AAC-002 | **Cannot request what you already have.** A member with ACTIVE access to the product cannot raise a new request for it (400 "You already have access to {product}."). | backend | REQ-TEN-010.1 |
| BR-AAC-003 | **One pending request per member and product.** A second request for the same member and product while one is still PENDING is refused (400 "You already have a pending request for {product}."), backed by a database partial unique index (`uq_access_request_pending`). | backend + database | REQ-TEN-010.2 |
| BR-AAC-004 | **Cancel only while pending.** Only the request's own requester may cancel it, and only while it is PENDING (400 otherwise); a decided request is a historical record. | backend | REQ-TEN-010.3 |
| BR-AAC-005 | **Approve = the same grant an administrator makes.** Approving calls `AccessSyncService#grantProduct`, the identical path and seat check an administrator's direct grant uses ([REQ-TEN-005](../access-management/requirement.md) BR-8); a request cannot be approved past the product's seat limit. | backend | REQ-TEN-010.5 |
| BR-AAC-006 | **Reject needs a reason.** Rejecting a request without a non-blank note is refused (400 "Write a reason for rejecting this request."); the note is capped at 500 characters. | backend | REQ-TEN-010.6 |
| BR-AAC-007 | **No auto-decide, decide once.** No access request is ever auto-approved or auto-rejected. A request already APPROVED, REJECTED or CANCELLED cannot be approved or rejected again (400 "This request has already been decided."). | backend | REQ-TEN-010.7 |
| BR-AAC-008 | **Single-level approval only.** One organization administrator or *Manage product access* holder decides a request; there is no second approval level or amount-based rule ([C103](../../../01-business/roadmap/open-decisions.md#c103)). | backend | REQ-TEN-010 (out of scope) |
| BR-AAC-009 | **Cross-organization isolation.** Listing, approving or rejecting checks that the request's member belongs to the caller's own organization (403 "You do not have permission to do this" if not — a different organization's admin never gets a 404 that would confirm the request exists in theirs, nor a 403 that reveals it belongs elsewhere if the id is simply wrong, which instead 404s). A member's own `myRequests`/`cancel` only ever reaches their own rows. | backend | REQ-TEN-010.8 |
| BR-AAC-010 | **Self-removal is immediate and unapproved.** "Remove my access" requires the member to currently have ACTIVE access to the product (400 "You do not have access to this product." otherwise); it revokes the access at once via `AccessSyncService#revokeProduct` and releases the seat immediately. It never changes, suspends or cancels the organization's subscription to that product. Getting access back afterwards always needs a new request — there is no reinstatement. | backend | REQ-TEN-010.9 |
| BR-AAC-011 | **Subscription-driven revocation is unchanged.** Cancelling, suspending or expiring an organization's subscription already revokes every member's access to that product automatically (`SubscriptionService#afterOrganizationChange` → `OrganizationEntitlementsChangedEvent` → `AccessSyncService#onEntitlementsChanged`); this FRD adds no new behavior here, only documents it ([C103](../../../01-business/roadmap/open-decisions.md#c103)). | backend (existing, unchanged) | REQ-TEN-010 (out of scope) |
| BR-AAC-012 | **Order reminder is once-only and never decides.** A purchase request (`Order`) still SUBMITTED `PENDING_REMINDER_DAYS` (3) days or more after creation is reminded exactly once — `remindedAt` is set on the first reminder and checked before sending again. The job never changes the order's status; only `approveOrder`/`rejectOrder` do. Reminders are sent to every ACTIVE `ORG_ADMIN` of the order's organization. Disabled in tests via `app.orders.job-enabled=false`. | backend | REQ-TEN-010.10 |
| BR-AAC-013 | **Notifications and audit.** A new request notifies every ACTIVE member holding `MANAGE_PRODUCT_ACCESS` or the `ORG_ADMIN` role (`ACCESS_REQUESTED` audit). Approval notifies the requester (`ACCESS_REQUEST_APPROVED` audit, plus the existing product-access-granted notice). Rejection notifies the requester with the reason (`ACCESS_REQUEST_REJECTED` audit). Self-removal writes `ACCESS_SELF_REMOVED`. A failed notification never fails the underlying change (same pattern as every other notification in the codebase). | backend | REQ-TEN-010.11 |

Rules shared with other features belong in `docs/03-business-rules/` and are referenced here by ID. [BR-ACC-001 Effective access](../../../03-business-rules/BR-ACC-001-effective-access.md) and [access-management's business rules](../access-management/business-rules.md) (BR-1 to BR-16) govern what "having access" and "a free seat" mean; this feature only adds how a member reaches that state by themselves.
