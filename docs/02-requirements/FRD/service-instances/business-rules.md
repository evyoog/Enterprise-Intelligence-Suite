# Business rules — Service instances (REQ-SRM-001)

Decided in [C101](../../../01-business/roadmap/open-decisions.md#c101) (SR-1 to SR-5, 2026-10-14). Enforced by the backend; the cited class and method are the source of truth.

| ID | Rule | Enforced in | Source |
|---|---|---|---|
| BR-SRM-001 | **One instance per subscription** (`service_instance.subscription_id` is unique). An instance is created when the subscription is `ACTIVE`; a subscription in any other status that has no instance yet gets none. It records the product, and the owner (organization, or the individual customer). | backend, database | .1; `ServiceInstanceService#syncFromSubscription` |
| BR-SRM-002 | **The instance follows its subscription.** New instance: `PROVISIONING`. Subscription `ACTIVE` again after `SUSPENDED` or `DEPROVISIONED`: `PROVISIONING`, or `ACTIVE` if the instance has reported before. Subscription `SUSPENDED`: `SUSPENDED`. Subscription `CANCELLED` or `EXPIRED`: `DEPROVISIONED`. An `ACTIVE` subscription never overrides `ACTIVE`, `PROVISIONING` or `FAILED`. The change is recorded as made by `SYSTEM` with the note "Subscription {status}". It runs from the subscription flow (`SubscriptionService#publish`) and, as a safety net, every 15 minutes (`ServiceInstanceReconcileJob`, `app.service-instances.job-enabled`). | backend | .2; `syncFromSubscription`, `#reconcile` |
| BR-SRM-003 | **Health values:** `HEALTHY`, `DEGRADED`, `DOWN` (reported), and `UNKNOWN` (before any report). A product may not report `UNKNOWN`. An administrator may set any of the four by hand. | backend, database (CHECK) | .3 |
| BR-SRM-004 | **Reporter key.** A platform administrator creates one for a product (a label is optional, up to 100 characters). The key is `eisrk_` followed by 43 random URL-safe characters; it is returned **once**, in the answer to the creation. Only its SHA-256 hash and its first 12 characters (a prefix, to recognise it) are stored; no API returns the key or the hash again. A key can be **revoked**; revoking is permanent and repeating it changes nothing. Creating and revoking are audited. | backend, database | .4, .10; `#createKey`, `#revokeKey` |
| BR-SRM-005 | **A report is authenticated by the key alone** (`X-Reporter-Key`). A missing, unknown or revoked key is refused with 401 "Invalid or revoked reporter key." before any report is read. The key's `last_used_at` is updated on every accepted call. `POST /product-reports/**` is open at the URL level like the payment webhooks and is **not** protected by a user token. | backend (service), `SecurityConfig` | .4; `#report` |
| BR-SRM-006 | **A call carries 1 to 200 reports** (400 otherwise). Each report names its instance by `instanceId` or `subscriptionId` and is accepted or rejected **on its own**; the answer lists how many were accepted and rejected and one message per rejection ("Report 2: …"). A report is rejected when: the instance is unknown **or belongs to another product than the key's**; the health is not `HEALTHY`, `DEGRADED` or `DOWN`; the instance is `SUSPENDED` or `DEPROVISIONED`; the optional status is not `PROVISIONING`, `ACTIVE` or `FAILED`. | backend | .3, .4; `#apply` |
| BR-SRM-007 | **An accepted report** sets the health, the message (up to 300 characters), the time of the report, the tenant reference (up to 100) and the access URL (up to 500) when sent, and marks the instance as last changed by `PRODUCT`. An instance in `PROVISIONING` becomes `ACTIVE` with its first report; a status sent in the report (`PROVISIONING`, `ACTIVE`, `FAILED`) is applied. | backend | .2, .3; `#apply` |
| BR-SRM-008 | **No recent report.** A report older than **5 minutes** (`ServiceInstanceService.STALE_AFTER`), or none at all, is "no recent report": the instance is flagged `stale`, its health counts as `UNKNOWN` in the health filter and the summary, and it is left out of the status-page combination (BR-SRM-010). | backend | .5 |
| BR-SRM-009 | **Manual change.** A platform administrator may set an instance's status (`PROVISIONING`, `ACTIVE`, `SUSPENDED`, `FAILED`, `DEPROVISIONED`) and/or health. A **note is required** (400 "Write a note saying why you are changing this instance."), and at least one of status and health (400 "Choose a status, a health, or both."). Setting a health also sets the time of the last report to now, so the status page uses it. The instance is marked as last changed by `ADMIN` with the note (up to 300 characters) and the change is audited (`SERVICE_INSTANCE_CHANGED`, before and after). The new status is not checked against the subscription. | backend | .6; `#changeByHand` |
| BR-SRM-010 | **Status page derivation.** Of a product's instances, only those that are `ACTIVE` or `FAILED`, reported within 5 minutes and have a health other than `UNKNOWN` count ("reporting"). A `FAILED` instance counts as Down. With *n* reporting instances and *d* Down: **d × 2 > n → Major outage; d ≥ 1 → Partial outage;** otherwise at least one Degraded → **Degraded**; otherwise **Operational**. Exactly half Down is Partial outage, not Major ([C101](../../../01-business/roadmap/open-decisions.md#c101) SR-3 B). With **no** reporting instance the status is the one a platform administrator set by hand, or Operational if none was set. | backend | .9; `#derivedStatus` |
| BR-SRM-011 | **Maintenance wins.** A product whose manually set status is `MAINTENANCE` shows Maintenance whatever its instances report (source `MANUAL`). | backend | .9; `ServiceStatusService#toStatusDto` |
| BR-SRM-012 | **Source on the status page.** Each product's status carries `source` = `INSTANCES` (derived) or `MANUAL`, and, when derived, the numbers behind it: `reportingInstances`, `downInstances`, `degradedInstances`. The customer page says "Based on N reporting instances (x down, y degraded)". The manual note and update time stay those of the administrator. The business dashboard's service-status alert ([BR-PRT-001.6](../service-status-page/business-rules.md)) uses the same derived status. | backend, frontend | .9 |
| BR-SRM-013 | **Who sees what.** Platform administrators (platform permission `MANAGE_SERVICE_STATUS`, `/admin/service-status/**`) see every instance, including deprovisioned ones, and the reporter keys. An organization administrator (organization permission `MANAGE_ORGANIZATION`) sees only the instances owned by their own organization, **without `DEPROVISIONED` ones**, read-only; any other caller is refused (403). Individual customers have no instance list. | backend, `SecurityConfig` | .7, .8; `#listForOrganization` |
| BR-SRM-014 | **Summary.** The summary counts the instances that are `ACTIVE` or `PROVISIONING` (optionally of one product): total; of those with a recent report, healthy, degraded, down and unknown; and those with no recent report. | backend | .7; `#summary` |
| BR-SRM-015 | **Provisioning is not built.** The instance is created by the subscription, not by a "provisioned" reply ([REQ-ORD-002](../provisioning-contract/requirement.md)). The tenant reference and access URL arrive in reports or stay empty. | backend | .1 |

Rules shared with other features belong in `docs/03-business-rules/` and are referenced here by ID.
