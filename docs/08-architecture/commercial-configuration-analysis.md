## 1. Executive summary

The reference document is a well-reasoned review of a *proposed* plan, not a description of EIS as it exists. Comparing it to the actual codebase changes the picture in one important way the reference document could not know, because it was written without seeing the code: **large parts of what it proposes were already decided against, by the product owner, earlier today, in [C104](../01-business/roadmap/open-decisions.md#c104).**

- **C104 OF-2, option D (final):** "a bundle has no price of its own and never will unless revisited; offerings only group products, and each product stays bought separately." The reference document's entire 12-step builder is built around **Step 4 Plans & pricing at the offering level** — an offering/bundle with its own plans, prices, discounts and a pricing chart. That premise is the opposite of what was just decided.
- **C104 OF-8, option A (final):** "every product is sold in every region; 'allowed regions' is dropped from the product rules." The reference document's **Step 5 Availability** (per-offering regions) and **Step 7 Eligibility** ("allowed regions") do not apply under that decision.

This does not mean the review is worthless — most of its findings are about things *underneath* offering-level pricing (a pricing service, versioning, entitlements, limits, permissions, migration) that are real gaps regardless of whether offerings ever get their own price. But before reading further, the product owner needs to pick one of two paths, because they cannot both be true (**CC-1**, below):

- **(a) C104 stands.** Offerings stay exactly as built (REQ-CAT-005): a free grouping of products with eligibility, compatibility and a "works with" list, no price, no regions. The 12-step builder, bundle pricing and per-offering regions in the reference document are **not built**. Most of the reference document's findings (G1, G4, G5, G7 as it applies to offerings, G8, G9, G10, G12 as it applies to offerings, G13, G14, G15, G19 as it applies to offerings) become **moot for offerings** — they would matter only if C104 is reopened. What *does* still apply, regardless of C104, is covered in §3 below: a real pricing service (G2), per-plan price points for multiple currencies/periods (part of G9/G10, since a *product's* plan already has this problem, bundle or not), plan versioning so a price edit doesn't silently change what existing subscribers pay (G7, which is a **real, current, already-exploitable gap**, not a future one — see CC-9), a feature registry (G16), limit precedence and enforcement (G4/G5/G6), permissions (G18) and migration (G23).
- **(b) C104 is reopened.** The product owner wants bundle pricing and/or per-offering regions after all, superseding today's decision. In that case the reference document's full scope applies, and the phased plan in §9 is the one to follow in order, starting with the decisions in §3.

**Readiness today:** the platform has a real catalog (`Product`), a real plan model (`ProductPlan`), a real offering/eligibility/compatibility layer (`Offering`, built per C85/C104), a real cart/checkout/order/payment/invoice/subscription/tax stack, and a real (if coarse) entitlements check. It has **no pricing service, no feature registry, no limit registry, no plan or offering versioning, and no multi-currency/multi-period price points** — these are the genuine gaps whichever path (a) or (b) is chosen. The single biggest risk if this is built without deciding path (a) vs (b) first is wasted work: building a 12-step bundle-pricing builder only to have it conflict with a decision made the same day.

## 5. Proposed domain model

Reflecting CC-1 = A (C104 stands) as the default path; the parenthetical notes what changes if CC-1 = B.

```
Product (existing)                     Offering (existing, C85/C104)
  |                                       |
  +-- ProductPlan (existing, extended)    +-- productIds (ordered, existing)
  |     |                                 +-- ProductEligibility (existing)
  |     +-- Price point (NEW)             +-- ProductCompatibility (existing)
  |     |     period x currency           |
  |     +-- Feature entitlement (NEW)     (no price, no regions — final, C104)
  |     |     plan -> feature ID          (if CC-1 = B: + Price point, + Region,
  |     +-- Limit value (NEW)              on Offering, mirroring ProductPlan's)
  |           limit type -> value, mode
  |
  +-- dependsOn (existing, Product.dependsOn — unchanged)

Feature registry (NEW, per product)      Limit type registry (NEW)
  stable feature ID, display name          name, unit, "enforced" or "informational"

PricingService (NEW)                      ProductSubscription (existing, unchanged)
  input: planId, quantity, currency,        references planId; CC-9 decides whether
         customer/org context               it also snapshots the subscribed price
  output: list, discount, final, rounding
  (the cart is refactored to call it instead of computing inline)
```

**What's new, regardless of CC-1:** price points (period × currency per plan), a feature registry + plan-to-feature matrix, a limit-type registry, and a shared `PricingService`. **What's new only if CC-1 = B:** the same three structures repeated at the offering/bundle level, plus a bundle-plan-to-component-plan mapping (G8).

## 6. Data migration plan

- **Nothing existing is renamed, removed or re-typed.** `ProductPlan.price`/`billingPeriod`/`currency` stay as the plan's default/display price; price points are an *additive* table (`plan_price_point`: plan_id, billing_period, currency, amount, region nullable) that, when present, takes precedence over the flat fields for display and checkout; when absent, the existing flat fields keep working exactly as today — so no existing plan needs a migration script, only new plans need price points populated.
- `usageLimit`/`overageCharge`/`tierPricing` on `ProductPlan` are **kept as-is** (G23) — the new limit-type registry supplements them for any newly-added limit types; it does not replace these three existing fields.
- `ProductSubscription.planId` and `Invoice`'s own snapshot fields are untouched; CC-9's resolution (whichever option) only adds a new nullable "subscribed price snapshot" field to `ProductSubscription` if option B is chosen — never a breaking change.
- `Offering` gets no new columns unless CC-1 = B.
- **Rollback:** every migration here is additive (new tables, new nullable columns) — rollback is "stop using the new columns/tables," no destructive down-migration is needed, consistent with how V001–V044 have all worked in this repository.

## 10. Acceptance criteria (representative, Given/When/Then)

- **Plan ownership (CC-2):** Given a plan edited on the product page, when an offering references that product, then the offering's displayed plans update immediately with no separate copy to keep in sync.
- **Pricing consistency (CC-3):** Given a plan with a 10% coupon applied, when the cart and the `/pricing/quote` endpoint are both asked for the same plan/quantity/currency, then they return the same final price to the cent.
- **Renewal-price safety (CC-9):** Given an existing subscriber on a plan whose price is later changed, when their next renewal invoice is generated, then (option A) a notice was sent at least N days prior, or (option B) the invoice uses their snapshotted price — never a silent, unnotified change.
- **Price points (G9/G10):** Given a plan with an INR monthly price point and a USD annual price point, when a customer in each region requests a quote, then each receives their own currency's price, never a converted or missing one.
- **Migration (G23):** Given a plan created before this feature existed, when it is read by any new code path, then its `usageLimit`/`overageCharge`/`tierPricing` values are unchanged and its subscribers' invoices remain unaffected.
- **Permissions (G18):** Given a customer-support role with no `MANAGE_CATALOG` permission, when they call any new admin pricing/limit endpoint, then they receive 403.
- **Dependency enforcement gap (found during this review, not this feature's to fix, but worth a ticket):** Given a product with `dependsOn` set, when a subscription is created through `SubscriptionService.subscribe` directly (not via cart), then today it succeeds even without the dependency — flag as a separate, pre-existing bug, not blocking this feature.

## 11. Risks and mitigations

| Risk | Area | Mitigation |
|---|---|---|
| Building the 12-step builder before CC-1 is answered wastes the whole effort if C104 is reopened later (or vice versa) | Billing/scope | Decide CC-1 first — it is a one-sentence product-owner confirmation, not a technical task |
| A plan price edit silently changes what existing subscribers pay at renewal (G7, CC-9) | Billing trust | Decide and build CC-9 independently and first, regardless of the rest of this plan — it's a live gap today |
| Two plan-editing screens drift apart if CC-2 is skipped | Data integrity | Keep plans product-owned (CC-2 = A); do not build a second editor |
| A feature registry migration breaks existing free-text feature matching mid-flight | Entitlement checks | Keep free-text matching working during a transition; add registry IDs additively, migrate plan-by-plan |
| Limits labeled "Enforced" that are not actually enforced | Customer trust | CC-7's labeling requirement is a hard rule: never show a limit as enforced unless code enforces it, matching this project's existing "do not promise limits the backend cannot enforce" rule |
